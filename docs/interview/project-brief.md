# 项目材料包

## 一句话定义

这是一个面向法律合规场景的 AI 应用项目，通过统一聊天路由、RAG、Agent、流式合同审查与降级策略，把“多模型能力”做成一个可演示、可解释、可验证的工程化系统。

## 3 个最强亮点

1. **统一多模型接口**
   - 用同一套 API 对外暴露 `BASIC / ADVANCED / ADVANCED_RAG / UNIFIED`，把多能力系统收敛成前端易用接口。
2. **RAG + Agent 协同**
   - 用高级 RAG 解决 grounding 和引用可控，用 Agent 解决复杂分析和工具调用。
3. **工程可信度补齐**
   - 有 fallback、metadata、异步流、测试回归、演示脚本和评测资产，不是只展示“功能截图”。

## 3 个技术取舍

1. **同时使用 Spring AI 和 LangChain4j**
   - 取舍：增加一点理解成本，换来“模型接入层”和“高级检索链路”的职责分离。
2. **保留多模式，不强行只留一个智能模式**
   - 取舍：增加系统复杂度，换来成本、能力、可复现性的不同选择。
3. **云端演示优先 DeepSeek，本地复现保留 Ollama**
   - 取舍：线上 demo 更稳定，本地工程复现能力也保住了。

## 3 个踩坑与修复

1. **高级模型不可用时直接报错**
   - 修复：`ADVANCED` 改为优先 DeepSeek，不可用时 fallback 到可用路径。
2. **统一聊天返回不够可解释**
   - 修复：稳定输出 `actualModel / routeReason / fallbackUsed / sourceCount / latencyMs`。
3. **合同分析流接口用 query token 不适合正式演示**
   - 修复：新增 `Authorization` Header 认证版本，旧接口只保留兼容。

## 5 个高频追问标准回答

### Q1：为什么不是所有问题都统一走一个模型？

因为法律场景里“简单问答”和“复杂分析”的最优链路不同。简单问题更适合稳定、便宜的 RAG；复杂问题则更适合 Agent 推理。统一对外接口，不等于内部只保留一条链路。

### Q2：为什么要做 fallback？

AI 系统最容易被质疑的点是“不稳定”。如果高级模型一不可用，整条链路直接挂掉，项目很像 demo。fallback 的价值是把系统从“能跑一次”提升到“可持续演示、可持续交付”。

### Q3：为什么前端要展示 metadata？

因为 AI 项目最难讲清楚的是“这次到底发生了什么”。把模型、路由原因、知识库来源、降级、延迟直接显示出来，演示时可解释，排查时也更快。

### Q4：为什么合同审查要做流式而不是同步接口？

合同分析耗时长，如果同步阻塞，用户体验很差，而且演示时看起来像“页面卡住”。SSE 能把进度、阶段、结果拆开实时展示，更像真实业务系统。

### Q5：如果面试官说这个项目还是偏 demo，怎么回应？

我会强调这轮不是盲目加功能，而是围绕“工程可信度”补齐了测试、降级、接口语义一致性、评测数据集、演示脚本和材料包。这些都是把 demo 往可交付系统推进的关键工作。
